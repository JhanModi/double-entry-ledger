# ADR-0021: Request ids and strict request parsing

- **Status:** Accepted
- **Date:** 2026-10-02

## Context
- **Tracing:** when a client reports an error, support must find every log line and database row the request produced. `CLAUDE.md` requires a request id on every log line.
- **Parsing:** JSON parsing is lenient by default. A JSON library may quietly turn `10.5` into `10`, or the string `"1050"` into the number `1050`, so a money API could move an amount the client never sent. Unknown fields are ignored (ADR-0017), so a typo in an optional field (`"descripton"`) is silently dropped.

## Options considered
- **Request ids**
  - *Taken from the client's `X-Request-Id` when present.* Correlation across systems is easier, but untrusted input lands in the logs and the audit log, and ids can collide or be spoofed.
  - *Always generated by the server.* Unique and trustworthy. The client gets it back in the response.
- **Parsing**
  - *Lenient (the default).*
  - *Strict:* amounts must be JSON integers, and unknown fields are rejected. This is how Stripe treats unknown parameters.

## Decision
- **Each request gets a server-generated random UUID as its request id.**
  - It goes into the logging context (MDC) as `requestId`, so every log line written while serving the request carries it.
  - It's returned in the `X-Request-Id` response header and as a `requestId` property on every Problem Details response.
  - It's stored on audit, transfer, and funding rows.
  - The generator is injected, so tests can control it.
- **Request JSON is strict:**
  - Amounts must be JSON integers. A float (`10.5`), a string (`"1050"`), or exponent notation (`1e3`) gets 400.
  - Unknown fields get 400, and the response names the field. This **supersedes ADR-0017's point that unknown fields such as `clientId` are ignored**. A `clientId` in a request body now gets an explicit 400. The owner still always comes from the API key.

## Consequences
- **Any error a client reports can be traced** to the server's log lines and database rows through its request id.
- **An amount is never rounded, truncated, or converted** on the way in.
- **Clients can't add fields this API doesn't define.** New optional request fields are still backward compatible, because old clients don't send them.

## How to explain it
"Every request gets an id generated by the server. It's on every log line, in the response header, in every error body, and on the audit row, so one id connects a client's complaint to everything that happened. Parsing is strict: an amount has to be a JSON integer, and unknown fields are rejected. In a money API, silently rounding a number or ignoring a field is a bug the client never sees."
